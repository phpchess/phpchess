# phpChess 6 — Decisions

The user's decisions behind phpChess 6, copied from the 4.4 analysis (`phpchess44/PHPCHESS_ANALYSIS.md` §5) so they travel with the code. New decisions are added here first. A decision that is later replaced is struck through, with the replacing one named; it is never deleted. § references point into the analysis.

| # | Decision |
|---|---|
| A1 | No local setup yet; install whatever keeps it fully current. Target **PHP 8.4** (8.3 minimum), **MariaDB 10.11 LTS / MySQL 8.0+**; Composer for development, `vendor/` uploaded. Hosting stays plain shared hosting: the code may not *require* cron, SSH, Node or long-running processes; it detects and uses them when present (cron, `.htaccess` rewrite, unbuffered output). |
| A2 | **Mobile site and PayPal dropped.** A server-verified PayPal integration may come later as its own package. |
| A3 | **No live data.** No data migration, no upgrade path from 4.x, no md5→bcrypt rehash step. |
| A4 | Improvements and current libraries encouraged, in most cases required. Each library is still named in the plan. |
| A5 | **Clean break in look and feel**: modern design, easily replaceable skins, an install-specific look without touching code (§11.6). |
| A6 | Installs fail on shared hosting → **restructure the database** as part of the rebuild (§11). |
| A7 | **Voting tournaments kept** (one primary player vs. a group voting on each move), rebuilt with server-side vote resolution. |
| A8 | **Clubs dropped.** |
| A9 | **Activities dropped**, replaced by seamless access to **Lichess** learning content (§12.6). |
| A10 | **Team vs Team kept** as a tournament format. |
| A11 | **phpChess 6.0 — a complete rebuild** (answers Q1 of §6.1): new code base, 4.4 is the behaviour specification, reuse only what survives review (strings, avatar sets if licensed, rules knowledge). |
| A12 | **Correspondence-centred, with timed play down to 5+3** (revised 2026-11-18, replaces "real-time Blitz"): correspondence is the core; the shortest time control is 5+3 (admin may raise the floor to 10+0); no Bullet, no 3+0/3+2, no WebSocket in the core (§14.1). |
| A13 | **Schools as a target**: easy to run on their own servers, features switchable per install (e.g. direct messaging off). |
| A14 | **A local computer opponent that plays consistently weak** (about 600 Elo or lower), not just "Stockfish turned down". |
| A15 | **League designed from scratch** (2026-11-22), not copied from 4.4's League A/B, with a drag-and-drop interface for arranging players. No 4.4 reference install: the behaviour catalogue comes from the code reading in this document, and 4.4 is run only if one specific question needs it. |
| A16 | **Client-side libraries** (2026-11-22): JavaScript used extensively, under these rules:<br>• a permissive licence (MIT, BSD, ISC). The computer-opponent engine is the one named exception: GPL-3.0 is allowed for it because it is compatible with phpChess's AGPL, and no strong permissive engine with MultiPV is known (user, 2026-11-22);<br>• served from the install itself, never a CDN;<br>• no network access beyond the install's own server;<br>• suitable for children aged 5 and over (no ads, tracking, third-party content or unmoderated external links);<br>• works fully offline;<br>• no known vulnerabilities.<br>"No known vulnerabilities" is checked, not assumed: versions pinned, `npm audit` / OSV check at every update, CSP `connect-src 'self'` so the browser itself blocks any outside request. |
| A17 | **Install without expertise** (2026-11-22): anyone who downloads phpChess 6 from GitHub can install it on shared hosting (the likely case) or a VPS by copying the files, opening one web address and following the steps. Consequences:<br>• the release is a ready-made zip with `vendor/` and the built JavaScript included, so no Composer, npm or command line is needed on the host;<br>• it works when the host can't point the domain at `public/`: it installs into the web root or a subfolder, a root `.htaccess` routes everything to `public/`, and every non-public folder also carries its own deny rule;<br>• the installer proves those folders are unreachable from the browser and stops if they aren't, with a plain-language fix;<br>• Apache and LiteSpeed (most shared hosts) work out of the box; nginx (VPS) gets a ready config snippet shown by the installer;<br>• the installer only needs the database details and the admin account, writes the config itself, and locks itself afterwards. |
| A18 | **Mobile first** (2026-11-22): every page is designed for a phone first. The site installs from the browser to the home screen (PWA) and receives notifications there by Web Push: on iPhone from iOS 16.4, after "Add to Home Screen"; on Android in Chrome and the other major browsers. Native apps for iOS and Android are built only if Web Push proves not good enough in C2-2. **Cost noted**: Web Push sends through the browser makers' push services (Apple, Google, Mozilla). That is the one outgoing connection, from the server, and the device's own browser connects to it too. It runs only while the "push notifications" switch is on, so an offline school install switches it off and keeps in-app notices and email. |
| A19 | **Improve, don't replicate** (2026-11-22): 4.4 is a starting point, not the specification. Starting a game is one tap. There is no wall between correspondence and live play: one game model with any time control. The site knows who is online: moves appear live while both players are there, a push notice goes out when the opponent has left, and a move email when they are offline. |
| A20 | **Modern capabilities throughout** (2026-11-22): drag-and-drop for moves and for arranging anything (League divisions, admin lists, uploads), live updates instead of reloads, share links and QR codes for invitations, offline viewing of your own games, dark mode. Each follows A16. |
| A21 | **Readable, documented code — an overarching mandate** (2026-11-22), like mobile first: every file is written so that a person can read it, find where to change something, and understand it without tools or AI. A PHP student should be able to study the code on their own. Clean names, clear segments, a description at the top of every file and above every non-obvious block. This is the project's main value: code that is easy to audit, secure and transparent. **Readability is never traded for efficiency, performance or brevity.** Where a faster or shorter way is less clear, the clear way wins. The only things that rank above it are correctness and security, and those are served by clear code too. |
| A22 | **Database names, table prefix and cleanup** (2026-11-22): every working phpChess database is called `phpchess`; the default table prefix is `phpc_` (tests use `phpc_test_`), never `pc_`; any non-working one (tests, CI, scratch) is called `phpchess_support`. Locally: `phpchess` for the site, `phpchess_support` for the tests. Pseudo-cron is on by default. phpChess 4.x had extensive database cleanup scripts for admins; 6.x keeps that ability as the cleanup job plus admin cleanup pages (C1-2 and later). |
| A23 | **The installer does everything, then removes itself** (2026-11-22): after copying the files, the web installer is the only thing needed, assuming the poorest shared host with PHP and MySQL (possibly on another machine). Only the database login from the hosting panel is asked; the database name is optional. The installer tries `localhost` and `127.0.0.1`, uses an existing `phpchess` database, creates `phpchess` (or `<account>_phpchess`) when allowed, uses the only visible database, or lets the visitor pick one, and explains every failure in plain words. It also creates the admin account. At the end it deletes its own files (`src/Install`, `templates/install`); if the host refuses, the lock (INS-06) still holds and the admin banner asks for the deletion. Database names from the visitor are the one allowed exception to K5's "identifiers from code": letters, digits and `_` only, during installation only. |
| A24 | **Skins are created in the admin area** (2026-11-22): admins build skins in the browser, including logo selection, colour schemes, default pieces, layout choices and fun seasonal effects, without touching files or code (ARCHITECTURE.md §7, UI-02). |
| A25 | **Skin editor later, skins ready for it now** (2026-11-23): the skin editor in the admin area and the seasonal effects (A24) are nice-to-haves and move to the backlog (B3), out of C1-2. C1-2 designs the skin so a simple editor can be added without changing it: one `skin.json` with plainly named settings (colours, fonts, logo, board, pieces, layout), one `theme.css` made only of CSS variables generated from those settings, and readable PHP and JavaScript around it. Theme ideas from common content management systems (WordPress and the like) and student portals are a backlog item too (B4). |
| A26 | **4.4 English strings as the base** (2026-11-23): the English language file starts from phpChess 4.4's `includes/languages/english.txt`; strings are reused where they fit, reworded where 4.4 was unclear. |
| A27 | **Security scan with OWASP ZAP** (2026-11-23): ZAP may be downloaded and installed on the development machine to scan the local site at the end of each block (ASVS level 2 review). |
| A28 | **Days per move** (2026-11-23): free choice with a slider, 1 day up to an admin-set maximum (admin option, 1–31 days, default 30); no fixed list. |
| A29 | **Vacation** (2026-11-23): 30 days a year, taken in whole days; it pauses the clocks in all of the player's correspondence games; timed games never pause. |
| A30 | **Ratings** (2026-11-23): start value 600, an admin option. A player is "newbie" (no rating shown) for the first 3 games, then provisional until 20 games with K=40, then K=20. Separate ratings for correspondence, rapid and blitz. **Self-rating at registration**: a drop-down (newbie, unknown, or a strength band), optionally backed by a short self-test of 5–10 basic puzzles; newbie or unknown starts at the admin start value (600). |
| A31 | **Own rules engine** (2026-11-23): the server rules module (G-01) is written in our own readable PHP and checked with perft tests; no PHP chess library. |
| A32 | **Browser libraries approved** (2026-11-23): cm-chessboard 8.15.8 and chess.js 1.4.0 may be downloaded, checked under A16 and kept locally. |
| A33 | **Abort is an admin option** (2026-11-23): free aborts can be misused to pile up game records against a player, so the admin decides whether a game may be aborted before move 1 (default: allowed, never rated, recorded). Timeout: the opponent wins, or a draw if the opponent can't mate. Admin choices for an abort before move 1: allowed (never rated, recorded), counts as a loss, or the player must ask an admin to abort with a reason. |
| A34 | **Move emails are an admin setting** (2026-11-23): mail after each move, once a day (digest), after an offline delay, or off; the admin sets the choices and the default, players choose among what is allowed. One-click link to the game. |
| A35 | **Challenge expiry is an admin setting** (2026-11-23): defaults are open 7 days, direct 14 days, invite link 7 days and used once. |
| A36 | **First board screen** (2026-11-23): board (drag or tap), move list, clocks, draw, resign, abort, flip, rematch, plus a **planning board** (legal moves only, the player moves both sides, never sent). Conditional moves go to the backlog. |
| A37 | **Admin adjudication and FEN** (2026-11-23): an admin sets a result and a reason from a fixed list, recorded in the audit log; the reason list and FEN rules are admin options. Default: players may use a FEN in direct challenges. |
| A38 | **C2-1 build choices** (2026-11-23, to review with C2-1): threefold repetition and the 50-move rule end the game automatically, nobody has to claim (A19). "Before move 1" for aborting (A33) means before each side has made its first move. A player counts as watching a game live when its page polled in the last 30 seconds (no notice then), and as offline after 5 minutes without a request (move emails). Move emails are sent only while the "email requirement" switch is on. Invite QR codes come from our own small encoder (byte mode, level M, up to 106 characters), no library. Self-rating at registration is the drop-down only; the self-test puzzles are backlog B15. |
| A39 | **C2-1 review changes** (2026-11-23): abort only before the first move (replaces that part of A38); abort button hidden otherwise. Moves only on the board, no typed-move field (no JavaScript: board shown, game buttons still work). Game page: big board, own line icons (no library), icon bar flip / planning / replay / PGN; replay mode with its own bar and the move list; planning board with title, admin-chosen colours (default blue), close button, no move list. Buttons show a pressed look and a busy spinner and can not be sent twice. Game lists show a mini board drawn by the server from the stored position (nothing stored). Start page lists games waiting for your move, 8 per page; "My games" in the top menu. PGN with/without chat waits for chat (C2-2). |
| A40 | **No Docker in C2-2** (2026-11-23): shared hosting has no root access, so a Docker image has no use for now. INS-09 leaves C2-2 and goes to the backlog. |
| A41 | **C2-2 defaults** (2026-11-23): school login codes are one-time codes printed as QR cards per class and revocable by the teacher (passkeys and picture PINs stay in B13). Messages arrive live while on the site (the C2-1 polling), otherwise as a notice and an optional push. Bundled avatars are our own simple SVGs; uploads are re-encoded by GD to PNG or WebP, 256 px at most. The newsletter goes through the job queue, at most N mails per run (admin setting, default 50). |
| A42 | **Retention by performance, not by age (SCH-07)** (2026-11-23): no data is deleted after a number of days, so nobody loses history (chat, messages, logs, games). The server measures response times. When a set cut-off is passed, it suggests an archive to the admin (on the admin page and by email). The archive writes the old rows to a file that the admin downloads and keeps locally (it can be read back in). Only after that do those rows leave the database. |
| A43 | **A42 details** (2026-11-23): each day the server times a fixed set of typical reads; the cut-off is 0.5 s by default and the admin can change it. The archive holds finished games, messages, chat and logs older than a date the admin picks; running games are never archived. The archive file is compressed JSON, one compact record per line, and can be read back in from the admin page. |
| A44 | **Notices off the menu, dashboard on the landing page** (2026-11-23): notices leave the main menu and the player's view; they stay stored for admin searches. The Play link shows a "my move" count instead. Logged-in users land on a wider dashboard: on the left, tiles with mini boards for My move and My games (opponent to move); on the right, text lists of Open challenges (one-tap accept), Live games to watch and the 10 most recent finished games. On a phone it is one column in that order. |
| A45 | **Fit to the server, never edit php.ini** (2026-11-23): phpChess tests what the server can do (ServerSupport). Without GD, picture uploads stay off (bundled avatars remain); without openssl, curl and mbstring, push stays off (email remains). The switch is greyed out with the reason; the installer lists both as optional. |
| A46 | **C3-1 timed play** (2026-11-23): fixed time controls 5+3, 10+0, 10+5, 15+10, 30+0, 30+20 and the standard 120+40 (minutes + seconds); the admin floor (A12) hides the faster ones. The opponent's clock starts when their page first receives the move (at most 2 s after it was saved), plus up to 300 ms network allowance per move (K12). Flag fall is checked inside the move lock on every move and poll, and by the clock job; a flag against a side that can never mate is a draw. Pace changes work both ways (timed ↔ correspondence) on proposal and acceptance; to timed needs both online and restarts both clocks at the base time; the rating category stays the one the game started with. No abort timer: the clock runs from the start, a player may wait and lose on time (A33 abort before the first moves stays). Open lobby offers show only while their poster is online. Disconnects never pause the clock; "opponent disconnected" shows after 10 s. One server-side premove, played at 0 ms, dropped when illegal. Polling every 1 s (opponent to move, timed), 3 s (own move), 10–30 s otherwise, version check first. Admin options with these defaults: 30 timed games on the site, 1 per player (raise it for simuls, backlog B19), poll intervals. A rules page is generated from the admin settings for players; the admin sees the same page from the settings screen. |
| A47 | **C3-2 engine** (2026-11-24): GarboChess stays the engine; phpChess does not ship or directly support Stockfish. `docs/ENGINE_HOWTO.md` explains how to plug in another engine (worker interface, licence note: Stockfish is GPL-3.0, A16). AI-01 updated. |
| A48 | **C3-2 selection layer** (2026-11-24): score all legal moves; choose among moves within a margin of the best, weighted towards the better ones. The random choice is seeded from game id + ply, so the same position and settings give the same move on every device. Missed tactics (forks, even a missed mate in 1) are allowed at low levels. **No sacrifices for nothing**: a move that hands material over at once with no gain confirmed by a deeper check is filtered out. Wood pusher (~0): random legal moves, no checks. 300–499: the filter is skipped now and then, less often as strength rises. 500 and up: always on, 0 such moves in the proof. |
| A49 | **C3-2 search depth** (2026-11-24): never time-based (same move on every device). Depth depends on the position: book moves in the opening (per-player book depth and variety; book in `public/assets/engine/book/`), base depth in the middlegame plus extensions while captures/checks remain (long central exchanges resolved by static exchange evaluation and quiescence), extra depth in the endgame. Up to ~1600 stays within depth 5 on phones; stronger players may search deeper, are marked "slow on phones" and show a thinking pause; the admin can cap the depth. |
| A50 | **C3-2 players** (2026-11-24): at least 60 computer players from ~300 to 2000+, plus a wood pusher, each with a personality: aggressive, defensive, trader, inconsistent (plays a band above or below its rating per game, seeded), teacher: moved to coach games, backlog B27 (A53); C3-2 games have no take-backs. Names, ratings, styles and avatars come from the user's Arc Chess project, asked for when the characters are built. Each is a system user with a computer flag, clearly labelled, hidden from player lists and ratings; games are stored, unrated, untimed. |
| A51 | **C3-2 calibration** (2026-11-24): a Node script `tools/calibrate.mjs` (development only, same JavaScript as the phones) runs overnight. Anchors: random mover (Elo 0), capture-first mover, GarboChess at full strength depths 1–8; ~12 anchor levels at 200 games per pairing, each personality placed with ~60 games against its two nearest anchors; BayesElo-style fit with 95 % ranges, published in `docs/proofs/c3-2-calibration.md`. Ratings above ~1200 are estimates with wide ranges (no human anchors). Admin engine page is read-only: engine name, version, licence, source, players and calibration result. |
| A52 | **C3-2 opening book** (2026-11-24): the book is the Lichess chess-openings list (`public/assets/engine/book/a.tsv`–`e.tsv`, CC0), used for book moves and opening names; the large rating-banded binary was dropped. `traps-sample.tsv` (popular losing opening moves with refutations, CC0) feeds low-level and teacher players. Both listed in LIBRARIES.md as CC0 data. |
| A53 | **C3-2 computer players** (2026-11-24): the list is `src/Domain/Computer/computer-players.json` (from the user's Arc Chess project): 60 players, 300 to 2000, five personalities of 12 each: Conservative, Aggressive, Balanced, Uneven (plays above or below its rating per game, seeded), Trader (prefers exchanges and simple endgames; 12 players moved from the other four, bios adjusted). Player 0 is the Wood Pusher (random legal moves, ~0). Faces: `public/assets/faces/computer/NNN.jpg` by player id (all 60, square, from the user's grid 2026-11-24); missing faces show the default avatar. Players 1400 and up are marked "slow on phones". Calibration adjusts a player's engine settings, never its listed Elo. Teacher games are separate from players (openings coach, full strength from a set position, play coach with mistake taxonomy, endgame coach, ...); see backlog. |
| A54 | **Updates from the admin pages only** (2026-11-24): a waiting database update shows in the admin banner with one button, "Run updates now" (logged-in admin, password confirmed). The setup token and reopening the installer are removed: after the install the installer stays closed for good. No admin login, no update. Consequence for every later migration: it must keep the admin login and the admin pages working before it runs (only add, never break what login reads). |
| A55 | **C3-2 calibration against people** (2026-11-24): the engine ladder alone (random mover = 0) does not give human ratings. The computer players are matched to real players instead: `lichess_2022-12_scored_1000_per_band.pgn` (Lichess, CC0, 16,000 blitz games, 1,000 per band 600–2100, in ChessTutor\ExternalData) gives, per rating band, the average loss per move, the share of mistakes and blunders and of giveaways, all re-scored by GarboChess depth 5 so humans and our players have one judge; 60 games per band. The strength table is tuned until each player's profile matches its band; 300–500 continue the trend below 600, the Wood Pusher stays random. **Priority is the low end** (beginners, students, clubs: 300–1200, empathetic play); no player searches deeper than depth 5; ratings above ~1600 are less important. Coach games (B27) use GarboChess at full strength. The donated Polyglot book (OpeningBook.bin) is not used: nothing owed, and players use many unconventional openings anyway. |
| A56 | **C3-2 human-like mistakes** (2026-11-24, replaces the "never from 500 up" part of A48): computer players give material away at the rate people of their band do (Lichess profile, A55), about 6 % of moves at 600, 2.5 % at 1000, 1 % at 2000, more below 600; the filter stays and decides how often, not whether. Each band gets chances for a mistake, a blunder and a giveaway on top of its margin; depth 1–2 below 1200, at most 3–4 above. Tuning is done once: a carefully calculated first setting, one profile run, then one final adjustment (no repeated fitting loops). |
| A57 | **C3-2 how weak players play** (2026-11-25, replaces the mistake and blunder chances of A56 and the margin of A48 for players): weak players do not play bad moves on purpose, they do not see the good ones. Three knobs per rating besides depth: **noise** (each move's value is blurred at random: small positional differences vanish, so low players have no plan; material differences survive, so they still recapture and save the queen), **blind spots** (in some moves the player does not see tactics: mates, winning captures and checks, never a recapture; a sound combination is not a giveaway, its gain is seen), **giveaways** (A56, kept: they matched people). Mistake/blunder chances and their automatic correction are removed (the judge at depth 5 and the player at depth 1–3 disagree, so correcting towards the judge ran away). A short indicative run (120 games) first, then the 600-game run. |
| A58 | **C3-2 threat blindness** (2026-11-25): after the indicative run our players still lost far less per move than people (600: 63 against 93; 2000: 10 against 40). People lose most by not seeing the opponent's threats. So in some moves (30 % at 300, falling to 2 % at 2000) the player does not look at the reply: attacked pieces are left, threatened mates and forks go unseen; moving a piece onto an attacked square still counts as a giveaway, so giveaways do not rise. Also more noise at every rating and one depth less from 800 up (depth 1 up to 950, 2 for 1100–1400, 3 from 1550). |
| A59 | **F1 strength test data** (2026-11-25): Lichess puzzle database (CC0), downloaded once into a folder outside the repo; a script picks ~60 puzzles spread over 600–2200 into `src/Domain/Strength/strength-puzzles.csv` (68 puzzles, 9 KB; next to the code like computer-players.json); the full file is never committed. Listed in LIBRARIES.md. |
| A60 | **F1 strength test** (2026-11-25, B15): 10 puzzles, adaptive (harder after a solve, easier after a miss), solved by moving on the board, no time limit; result is the A30 strength band, stored like the drop-down choice; retake at most every 30 days. Pops up (dismissible) on the first login; until the strength is known a "Find your strength" link sits next to the rating; skipping keeps the drop-down. |
| A61 | **F1 chat** (2026-11-25, B17): no chat posts on finished games or games against the computer (server refuses, box hidden); posting no longer redraws the active board colours. Clear-cause findings of the C2-2 review are fixed in F1, larger ones go to the backlog. |
| A62 | **F1 service worker** (2026-11-25, B20): cache name = version from `src/Version.php` + short hash of the asset files. |
| A63 | **F1 site-wide poll** (2026-11-25, B21): as in B21 (15 s, 60 s in a hidden tab, Accept/Decline pop-up, push for direct timed challenges). The interval is an admin setting (default 15 s); B22 later suggests safe values. Load test updated, run only with the user's go. |
| A64 | **F1 board flicker** (2026-11-25, B23): all five steps of B23. |
| A65 | **F1 computer move delay** (2026-11-25, B30): default about 5 s ± up to 4 s per move (well inside 40 moves in 5 minutes); games against the computer have no clock (A50), so waits are fixed by the choice and never drift long. Each player chooses in their settings: none / short (~2 s) / normal (~5 s) / long (~10 s). |
